给 Bash 增加命令记录，适合补充交互操作的上下文。设计时需要先明确记录的含义，再决定采集位置。本篇只讨论通用实现思路，不提供部署脚本；重点是采集范围、事件语义和验收方法。

## 01 / 先定义一条记录代表什么

- 输入记录：操作者在 Shell 中提交的文本，用于理解操作意图；其中可能包含变量、函数和复合语句。
- 执行记录：Shell 内部执行单元或外部程序的启动事件，用于确认具体执行路径。
- 结果记录：Shell 返回的状态、应用返回的信息或实际资源变化，需要分别解释。
- 会话记录：终端输入输出与交互顺序，用于复现过程，但不天然等于结构化命令清单。

一行输入可能产生多个进程，也可能只调用内建命令。预先规定统计口径，避免把“采集到多少条事件”直接写成“执行了多少条命令”。记录缺失的字段也应明确标记，不能靠推测补齐。

## 02 / 将 history 作为辅助线索

Bash 历史记录受 `HISTCONTROL`、`HISTIGNORE`、历史容量和写入时机影响；不同会话还有并发更新问题。它适合帮助回顾操作，不应单独承担完整性与身份可信度要求较高的审计。

- 先区分交互与非交互、登录与非登录 Shell，依据启动文件规则确认采集入口覆盖哪些场景。
- 明确多行输入的保存形式、会话之间的隔离方式，以及何时持久化。
- 把历史文本看作一种来源，不承诺它等于展开后的参数、完整进程树或最终结果。
- 用户可修改的 Shell 状态与文件，应在方案中标明信任边界。

## 03 / 按事件粒度选择 Shell 钩子

`PROMPT_COMMAND` 在交互式主提示符出现前运行，适合整理上一轮交互的上下文，但不会为脚本中的每一步都产生完整记录。`DEBUG` trap 在多类执行节点之前触发，粒度更细，也更容易产生重复、递归和额外开销；它不是“一行输入只触发一次”的接口。

- 将钩子入口处的状态保存作为独立设计点，防止采集逻辑覆盖 `$?` 与 `PIPESTATUS`。
- 区分流水线整体状态和各阶段状态；解释整体状态时要考虑 `pipefail` 设置。
- 为开始、结束与未完成事件规定配对规则。只有结束侧钩子时，不宣称已经取得准确执行耗时。
- 核对函数、子 Shell、命令替换与 trap 继承行为，并与已有提示符工具兼容。
- 将 `BASH_COMMAND` 等变量视为当前执行上下文线索，不承诺单个字段能够还原全部原始输入。

## 04 / 设计能够关联的最小事件

建议先确定字段及来源，再选择存储格式。基本关联信息可包括主机标识、启动标识、Shell 会话标识、进程与父进程标识、会话内序号、采集时间和工作目录。

- 登录身份与当前有效身份分别记录；无法可靠获取时保留未知状态。
- 输入文本、执行上下文与结果状态使用不同字段，保留来源类型和采集器版本。
- 工作目录注明采集时机，避免把操作后的目录误当成操作前目录。
- PID 与终端名称可能复用，关联时同时考虑主机、启动周期、会话与时间。
- Shell 上报的身份属于客户端声明，接收端应另存可信接入身份，避免混成同一种证据。

## 05 / 让采集与交互操作解耦

实现时可将 Shell 钩子限制为少量本地操作，由独立采集进程负责缓冲、转发与重试。每次显示提示符都同步访问远程服务，会把日志网络故障带进交互路径。

- 为单条记录大小、本地队列容量与等待时间设定边界。
- 明确本地接收成功、持久化成功和远端保存成功是不同阶段。
- 为队列满、采集器退出和记录截断设计可观察的状态，避免静默丢弃。
- 在试点阶段选择故障时继续操作还是限制操作，并明确告警与恢复责任。

## 06 / 用覆盖清单验收

验证范围应包含内建命令、外部程序、多行输入、流水线、函数、后台任务、多个终端、嵌套 Shell、远程非交互执行和异常断开。每个场景先写预期：应产生什么事件、哪些字段可信、哪些阶段可能缺失。

先在少量测试账号中比较提示符延迟、重复率和已知样本的缺失情况，再扩大范围。Shell 退出或异常终止时可能没有下一次提示符；非 Bash 工作负载也不能被默认纳入覆盖。Shell 钩子仍运行在被观察的用户环境中，不能独立证明所有操作都已记录。
