命令审计从产生事件到可供调查，通常经过多个组件。每个组件都需要说明自己接收了什么、保存到哪里、失败时如何处理。本篇给出集中日志方案的实现思路，不提供采集器代码或服务端配置。

## 01 / 拆开交付链路的确认点

可先按“Shell 或系统事件、本地接收、缓冲、远程接收、持久化、检索”划分阶段，再为每段定义成功条件。写入本地接口不代表远端已保存，检索服务暂时不可用也不一定意味着底层数据已经丢失。

- 区分内存队列、磁盘队列与持久化确认，明确进程崩溃、断电和磁盘满各自可能损失的范围。
- rsyslog 的磁盘辅助队列仍会使用内存，不能只看到启用磁盘就认为每条记录都已落盘；需结合检查点、同步写入和正常退出策略评估。
- 为发送与处理设置合理边界，避免后端故障持续阻塞交互入口。
- 分别记录排队、接收、持久化和可检索的时间，定位延迟发生在哪一段。

## 02 / 统一字段，但保留来源语义

可以围绕事件标识、主机、启动周期、会话、进程、身份、采集器版本和源类型建立统一字段。Shell、Linux Audit 与 sudo 的原始语义仍应保留，不能全部压缩成一条无法解释的“命令执行成功”。

- 区分源时间、接收时间与会话内顺序；主机时钟偏差不应被隐藏。
- 系统调用返回值、Shell 状态和应用结果分别存储，避免同名状态字段含义不同。
- 对多行内容、控制字符与超长记录采用明确的结构化编码和截断标记，防止记录边界混乱。
- 日志中继或代理代发时，保存原始事件身份与转发身份，不能把代理进程的身份当成操作者。
- 关联失败、字段未知和解析失败应成为可检索状态，便于发现覆盖空白。

## 03 / 在首次持久化前处理敏感字段

命令参数、工作目录、重定向目标与终端输出都可能包含秘密或个人信息。建议先确定确有用途的字段，再决定是否收集原文。仅在搜索界面遮挡内容，无法清除此前进入缓存、日志文件或备份的敏感值。

- 优先减少采集范围，不自动收集完整环境变量或全部终端输出。
- 对确需保留的文本，在首次持久化前评估脱敏位置，同时注明被省略或变换的字段。
- 字符串匹配规则无法识别所有秘密，应结合参数类别、结构化来源和抽样检查持续改进。
- 若调查确需受限原始证据，应为其单独设计加密、访问权限与保留策略，明确普通检索使用的是脱敏视图。
- 公开案例只使用人工构造的场景，不能把真实日志删除几个显眼字段后就直接发布。

## 04 / 为重试、重复与乱序制定规则

可以采用经过认证的加密传输，并在远端不可用时保留受容量约束的本地缓冲。TLS 保护传输并认证对端，但不自动证明端点生成的每条事件都真实、完整。

- 保持事件标识在重试期间稳定，为重复接收设计幂等处理。
- 明确协议确认和存储确认的差别，不因为采用 TCP、TLS 或 RELP 就直接承诺端到端恰好一次。
- 以会话序号辅助发现缺口，不强行给所有主机事件构造没有证据支持的全局先后顺序。
- 为重试退避、队列上限、过期处理和证书更新制定策略，并让失败可见。
- 断网恢复后检查补传、去重与原始时间保留，而不只检查连接是否恢复。

## 05 / 将完整性与管理权限分开设计

集中保存可以降低单台主机故障或本地日志变更造成的影响，但仍需明确谁能修改采集配置、谁能查看内容、谁能删除记录。操作权限与审计存储管理权限分离，有助于减少单一账号控制整条证据链的风险。

- 按调查需要设定保留期限、访问范围和导出流程，同时记录对审计数据自身的访问与变更。
- 如采用摘要或签名，需要说明可信密钥和校验基准保存在何处；可同时重写数据与摘要的主体仍能破坏验证意义。
- 不可变保留或独立存储能够保护已接收的数据，但不能补回采集之前或传输中已经缺失的事件。
- 备份与恢复验收应覆盖数据、索引重建和权限，避免恢复后扩大原始记录的访问范围。

## 06 / 用故障场景验证整条链路

验收应覆盖日志量突增、网络中断、接收端停止、磁盘满、证书失效、采集进程重启、日志轮转、时钟偏差和部分记录损坏。每个场景都写明允许的交互影响、数据损失边界、告警时限与恢复要求。

建议关注最旧待发送事件的年龄、队列深度、丢弃计数、解析失败、截断数量、接收延迟和采集配置变化。某台主机没有日志，可能是没有操作，也可能是采集链路失效；需要结合采集器健康状态和受控验证事件判断。

设计输入端时可参照[Shell 层采集思路](/notes/bash-command-audit-design/)，规划多种证据来源时可参照[Linux Audit 与 sudo 的互补设计](/notes/bash-command-audit-linux-audit-sudo/)。本系列描述的是方案与验收方法，实际覆盖能力需要在目标环境验证。
