Shell 层记录提供操作上下文，Linux Audit 可以提供命中规则的内核事件，sudo 则提供提权入口的线索。组合方案应让每种来源回答明确的问题，并保留它们之间无法确定的关系。本篇只描述设计和验证思路，不给出审计规则或安装配置。

## 01 / 区分程序启动与命令原文

围绕 `execve`、`execveat` 的审计，可以观察命中规则的程序执行请求。规划时需要核对目标内核、体系结构与实际工作负载，存在兼容 ABI 时也应确认规则覆盖。

- 执行参数不等于操作者最初输入的文本；变量展开、函数和脚本会改变两者关系。
- Shell 内建命令通常不会独立触发新的程序执行，仅记录 exec 类事件无法完整覆盖它们。
- 系统调用记录中的成功与返回值，描述的是该调用；程序成功启动并不代表后续任务成功完成。
- 文件变化或配置生效情况需要相应的文件审计、应用日志或资源检查补充，不能由程序启动记录直接推出。

## 02 / 保留登录身份与执行身份

Linux Audit 的 `auid` 表示审计登录身份，需与当前 UID、有效 UID 一起解释。设计中应验证登录链路是否正确设置登录身份，以及提权后能否保留有用的关联。

- 不把所有有效 UID 为 root 的记录都归给同一个人；同时核对登录会话和提权入口。
- 对未设置登录身份的服务和自动化任务，关联工作负载、调度来源与服务身份，保留无法归因的部分。
- 共享账号只能证明某个账号被使用，不能凭一个身份字段证明具体操作者。
- 容器中的用户与进程标识可能位于不同命名空间，关联时注明宿主机视角与采集来源。
- Shell 环境变量提供的用户名或来源地址可辅助定位，但不能替代经过认证的入口记录。

## 03 / 先组装事件，再关联会话

一个 Linux Audit 事件可能包含 `SYSCALL`、`EXECVE`、`CWD`、`PATH` 等多条记录。应按审计事件标识组织记录，再关联 Shell、认证和 sudo 来源，避免把每行日志当成一次独立操作。

- 在事件标识之外保留来源主机与启动周期，避免跨主机或重启后的编号混淆。
- 为不完整事件设置等待窗口与缺失标记，不能无限等待，也不能伪造不存在的字段。
- 保存原始记录的受控引用及解析版本，使后续能够解释字段如何形成。
- 关联 PID、父 PID、终端、会话与时间范围，避免仅凭时间相近就认定是同一操作。
- 工作目录、参数和路径也可能包含敏感信息，进入检索系统前需要明确处理策略。

## 04 / 明确 sudo 日志的层次

sudo 的事件日志可以记录提权请求；按配置启用的输入输出日志用于了解交互过程。部分版本还提供 `log_subcmds` 等子命令记录能力，采用前应核对平台支持与实现限制。

- 记录一次启动特权 Shell 的请求，不等于已经结构化记录其内部全部活动。
- 终端录制与程序执行审计是不同来源，应保留各自语义，避免重复计数。
- 子命令记录涉及程序执行，并不能自然补齐所有 Shell 内建行为或应用内部动作。
- 输入输出录制可能接触密码交互和敏感业务内容，应先界定录制范围、访问权限与保留期限。
- 远程发送能力与失败处理取决于配置；方案应明确本地、转发端和接收端分别确认了什么。

## 05 / 设计规则范围与失效行为

先从需要回答的审计问题推导规则，估算事件量与开销，再决定是否扩大覆盖。只保留成功事件可能漏掉失败尝试；只采集某个身份范围，也会留下服务或其他入口的空白。

- 用代表性工作负载评估高频进程启动、记录大小、内核积压与采集速度。
- 监控丢失计数、速率限制和磁盘空间，并明确积压或存储故障时的处理策略。
- 保留规则版本、变更记录与加载结果，使同一时间窗口的覆盖范围可解释。
- 评估锁定审计配置等保护措施前，先明确其影响、维护窗口和恢复方式；某些锁定需要重启才能解除。
- 主机上的高权限控制仍是信任边界，不能因开启 auditd 就承诺全部证据不可删除或伪造。

## 06 / 按证据链验收

选择可控测试场景，分别验证普通登录、提权、特权 Shell、外部程序、内建命令、后台服务、自动化执行与容器任务。验收记录应写出每种来源的预期事件、身份字段和已知缺口，而不是只展示一条成功日志。

再检查多记录事件组装、PID 复用、时钟偏差、日志轮转、采集器重启和转发中断。最终结论应说明哪些操作已经有相互支持的证据，哪些只保留单一来源，哪些仍不在覆盖范围。
